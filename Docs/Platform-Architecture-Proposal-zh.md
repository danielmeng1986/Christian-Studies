# 平台架构规范草案

**版本：** 0.1
**状态：** 讨论草案——不是当前有效架构
**范围：** 拟议中的多书籍 AI 辅助阅读平台

> Agent 使用的英文主文档：
> [`Platform-Architecture-Proposal.md`](Platform-Architecture-Proposal.md)。

英文版是面向 Agent 的提案依据。正式接受的决定必须在同一次修改中同步到两个语言版本。在本规范草案得到正式接受、当前核心规范也完成修订之前，当前有效架构仍然是 [`Architecture.md`](Architecture.md)、[`Reader-Architecture.md`](Reader-Architecture.md) 和 [`AI-Context-Architecture.md`](AI-Context-Architecture.md)。

## 1. 目的

本草案描述单本书实现被通用化之后，Christian Studies 的目标形态。它先确定逻辑边界和数据流，而不提前决定最终仓库布局、前端框架、数据库或部署方式。

目标不只是一个书架 UI，而是一个完整阅读环境：保存来源、审核 Markdown、交互式研读、透明的 AI Context 和持久知识共同组成一条可追溯的生命周期。

## 2. 架构驱动因素

平台必须：

1. 支持多本书，而不是把阅读器代码复制进每本书；
2. 导入不同格式，同时保存原件；
3. 在抽取结果和权威阅读正文之间保留人工审核；
4. 明确区分内容、用户数据、生成产物和索引；
5. 在迁移期间保持当前阅读器和用户数据可用；
6. 使 `ContextBuilder` 与具体书籍无关，并可独立评估；
7. 支持多个模型，但不把 Context 质量绑定在某个提供商上；
8. 通过明确能力和权限接入 MCP 与技能；
9. 在 AI 或网络不可用时仍然可理解、可阅读、可记笔记；
10. 从导入一直到 AI 回答都能看到证据与来源链；
11. 让结构化知识通过用户审核形成，而不是由 AI 静默修改。

## 3. 从当前实现到目标平台

| 关注点 | 当前实现 | 目标方案 |
| --- | --- | --- |
| 应用边界 | `Books/追寻敬虔/Web/` 拥有一个单书阅读器 | 一个共享应用操作已注册的书籍包 |
| 书籍发现 | 路径和常量知道唯一一本书 | 书籍目录解析稳定的书籍与版本身份 |
| 导入 | 书籍专用脚本与人工流程 | 格式适配器加可审阅的导入流水线 |
| 渲染 | 书籍本地的确定性构建器 | 消费书籍包契约的共享渲染服务 |
| 用户数据 | 通过受限 API 管理书籍本地 JSON | 保持同样的持久所有权，改用书籍无关接口 |
| Context | 已工作的书籍本地 `ContextBuilder` | 版本化 Context Service 和可插拔检索提供者 |
| 模型调用 | 单一配置的模型路径 | 用户可见、可以降级的策略型 Model Router |
| 工具与技能 | 很少或尚未接入 | 带授权、来源记录和最小权限的能力注册表 |
| 知识 | 主要是书籍本地笔记与讨论 | 与多本书和证据相连的已审核结构化知识 |

这是提取和通用化策略，并不要求替换当前使用的每一种技术。

## 4. 目标逻辑架构

```text
┌──────────────────────── 多书籍前端 ─────────────────────────┐
│ 书库 │ 导入/审核 │ 阅读器 │ 笔记 │ AI 讨论 │ 知识            │
└──────────────────────────────┬───────────────────────────────┘
                               │ 版本化应用 API
┌──────────────────────────────▼───────────────────────────────┐
│                           应用后端                            │
│                                                               │
│ 书籍目录       导入流水线             阅读器/构建服务          │
│ 笔记服务       讨论服务               补充资料库                │
│ Context Service   Model Router         Capability Gateway      │
│ Knowledge Service                   任务 / 迁移 / 验证          │
└───────────┬──────────────────┬───────────────────┬─────────────┘
            │                  │                   │
            ▼                  ▼                   ▼
      持久书籍包          用户拥有的数据        运行时/派生存储
   原件 + Markdown        笔记 + 授权状态       索引 + 缓存 + 任务状态
            │                                      │
            └──────────────────┬───────────────────┘
                               ▼
                         证据 Manifest / 审计
                               │
                    ┌──────────┴──────────┐
                    ▼                     ▼
                 已批准模型           已批准 MCP/技能
```

图中是逻辑服务。初期它们可以存在于同一个本地进程和仓库中。只有实际规模或部署决定证明有必要时，才拆成独立网络服务。

## 5. 持久书籍包

书籍包是内容与平台之间可迁移的边界。准确目录布局仍由 [OQ-005](Open-Questions-zh.md#oq-005-平台与书籍包边界) 决定，但逻辑上包含：

- 稳定的书籍与版本身份；
- 保存不变的主要来源文件；
- 经过审核的规范化 Markdown 阅读单元；
- 经过整理的参考资料和经文配置；
- 元数据和规范化来源链；
- 如果最终所有权模型把用户数据保留在书中，则包含注释和讨论；
- 可选的补充资料库记录；
- 验证和迁移书籍包所需的 schema 版本。

应用模板、共享 UI、模型客户端、通用转换适配器和通用索引代码不应复制进每一个书籍包。

即使不运行前端，书籍包也必须可以理解。平台索引和生成 HTML 可以删除后重建。

## 6. 导入与发布流水线

```text
接收来源
    ↓
记录身份、使用权、校验值和导入元数据
    ↓
保存不可变原件
    ↓
通过格式适配器抽取
    ↓
生成转换报告和审核预览
    ↓
人工修正与批准
    ↓
发布权威的规范化 Markdown
    ↓
验证引用、结构、元数据和来源链
    ↓
构建阅读器资源和检索索引
```

### 必要阶段

**导入登记**在转换前分配稳定身份并记录来源。转换失败不能丢失或修改原件。

**格式适配器**负责把受支持的 DOC/DOCX、PDF、EPUB、HTML、Markdown 或其他格式抽取成带诊断信息的共同中间结果。适配器不能静默地把自己的输出宣布为权威正文。

**审核工作台**显示抽取中的不确定项、标题结构、引用、脚注、图片和原始位置。只有经过人工批准，Markdown 才能升级为阅读正文的权威来源。

**验证**检查书籍包契约；必要证据或结构尚未解决时，阻止正式发布。

**发布**更新声明的阅读正文，然后重建可丢弃的阅读器资源和索引。它不能覆盖用户笔记或讨论。

## 7. 后端能力边界

### 7.1 Book Catalog

解析稳定的 `bookId` 和 `editionId`、生命周期状态、书籍包位置、可用章节、构建状态和验证状态。它不能把整本书复制进不透明的目录记录中。

### 7.2 Ingestion Pipeline

管理导入任务、适配器选择、转换诊断、审核产物和发布请求。没有所需的用户批准时，不得把转换结果升级为正式内容。

### 7.3 Reader and Build Service

通过共享模板或组件渲染经过审核的 Markdown 和参考资料。构建产物应尽可能确定性生成，并且不能包含笔记、讨论或授权状态的唯一副本。

### 7.4 Note and Discussion Services

负责用户数据的验证写入、修订冲突、schema 迁移和持久来源记录。阅读、构建和 Context 预览始终是只读操作。

### 7.5 Source Library

负责补充资料导入、处理、索引、隐私状态和逐来源外发资格。删除处理稿或索引不能删除原件，也不能静默改变授权。

### 7.6 Context Service

负责证据发现、分类选择、排序、预算、预览、来源修订验证和 Manifest 生成。它产生与模型提供商无关的 `ContextBundle`；它不决定持久笔记内容，也不静默调用工具。

### 7.7 Model Router

根据请求需要、Context 大小、工具要求、隐私限制、质量策略、延迟和预算，在明确配置的模型中选择。它消费与提供商无关的 Bundle，并生成可记录的路由决定。模型选择不能掩盖证据发生的变化。

### 7.8 Capability Gateway

统一管理 MCP Server、技能、外部研究和其他工具。它只暴露已经注册的能力，执行用户和来源权限，把工具结果作为分类明确的证据，并把使用情况写入每轮 Manifest。

### 7.9 Knowledge Service

为结构化笔记、实体、链接和综合内容创建建议。AI 建议在用户接受或编辑前，始终只是 AI 生成的工作材料；正式接受的知识必须保留证据链接和修改历史。

## 8. 前端信息架构

目标前端包含六个互相连接的工作区：

1. **书库**：书籍、版本、进度、验证状态和最近活动。
2. **导入与审核**：来源选择、转换诊断、Markdown 审核和发布批准。
3. **阅读器**：章节正文、导航、参考资料、主题和搜索。
4. **研读**：注释、讨论、补充资料和未解决锚点。
5. **Context 检查器**：证据预览、选择、预算、模型、工具、授权和 Manifest。
6. **知识**：已审核的结构化笔记和跨书连接。

这些工作区可以共享同一个应用外壳。在交互复杂度与维护标准得到决定之前，目标架构不指定前端框架。

## 9. AI 请求流程

```text
用户问题和当前阅读位置
           ↓
Context Service 发现候选证据
           ↓
用户可见的预览应用选择和授权
           ↓
Context Service 冻结并验证所选 Bundle
           ↓
Model Router 选择已批准模型与降级策略
           ↓
Capability Gateway 只运行明确允许的工具
           ↓
模型接收分类证据与行为指令
           ↓
回答流式进入阅读器
           ↓
讨论记录保存回答、模型决定和证据 Manifest
```

只有理解核心证据需求之后才进行模型路由。选择更强模型不能替代修复缺失、无关或错误分类的 Context。

## 10. 模型路由策略

未来的 Router 应考虑：

- 任务类别：解释、比较、综合、抽取或研究；
- 所需推理深度和可接受延迟；
- Context 大小和支持的输入类型；
- 是否需要工具或特定能力；
- 每一项来源的隐私和提供商资格；
- 质量评估门槛；
- 预计成本和成本上限；
- 提供商健康状态和安全降级方式。

UI 应显示选择的模型或策略层级，并在请求仍然有效且安全时允许用户覆盖。路由必须使用固定阅读任务评估，不能只凭对模型质量的印象。

## 11. MCP 与技能架构

MCP Server 和技能是受控能力，不是环境中的默认权威。每项注册能力应声明：

- 目的与输入输出类型；
- 本地或外部执行边界；
- 可以接收的数据类别；
- 需要的逐次确认或持久权限；
- 网络、文件系统、账户和写入影响；
- 结果携带的来源信息；
- 超时和失败行为；
- 测试或评估用例。

导入书籍、笔记、网页、工具结果和检索文档始终是不可信内容。它们不能自行获得能力权限，也不能覆盖系统行为。

## 12. 数据与持久化策略

无论最后选择哪种存储技术，都必须保留三个类别：

| 类别 | 示例 | 必要属性 |
| --- | --- | --- |
| 持久内容 | 原件、审核 Markdown、参考资料、元数据 | 可迁移、可追溯、可人工审阅 |
| 用户拥有的状态 | 笔记、讨论、授权、已接受知识 | 冲突安全、可恢复，不能只靠重建 |
| 运行时/派生状态 | 索引、缓存、Token 估计、构建资源、任务状态 | 可丢弃或从声明输入重建 |

持久用户状态是继续使用 Git 管理的文件、部分进入 SQLite，还是同时支持两种方式，仍由 [OQ-003](Open-Questions-zh.md#oq-003-持久存储与-git) 和 [OQ-006](Open-Questions-zh.md#oq-006-数据库角色) 决定。数据库不能成为没有文档说明的第二真相来源。

## 13. 安全与隐私

- 在部署策略改变前，本地服务默认只绑定 loopback。
- 提供商凭证只进入进程级秘密存储，不能进入内容、浏览器资源、日志或命令参数。
- 每次写入都必须针对已注册资源和 schema 版本验证。
- 所有导入和检索内容都按不可信数据处理。
- 同时执行逐来源外发资格和逐请求证据选择。
- 当策略要求用户决定时，在外发给模型或工具前显示数据范围。
- 记录模型、提供商、工具和证据来源，但不记录秘密。
- AI 服务不可用时，离线阅读和笔记仍应有用。

## 14. 评估与可观测性

平台需要在四个独立层面评估：

1. **转换：** 忠实度、结构保留和未解决歧义。
2. **检索与 Context：** 证据召回、无关证据、来源链和确定性。
3. **回答：** 事实依据、引用支持、聚焦程度和有用的不确定性。
4. **系统：** 延迟、Token、费用、失败、隐私决定和迁移完整性。

日志和 Manifest 必须区分用户内容与运行元数据，并避免保留秘密或不必要的私密正文。

## 15. 迁移策略

1. 用兼容测试冻结当前行为。
2. 在不移动内容的前提下定义书籍无关契约。
3. 把现有《追寻敬虔》实现包装在这些契约之后。
4. 通过目标导入路径构建第二本书。
5. 在两本书之外引入共享应用外壳。
6. 把 Context 组装移动到与模型提供商无关的 Context Service 后面。
7. 只有 Context 评估稳定后才增加模型路由。
8. 把受控能力和结构化知识分别作为独立垂直切片加入。
9. 只有数据和行为一致性得到验证后，才移除书籍本地应用代码。

每一步迁移都需要为持久用户数据提供回退或向后读取能力。目录移动和 schema 修改不能随意捆绑。

## 16. 实施准备门槛

结构性重构开始前，必须满足：

- OQ-001 至 OQ-006 已有正式接受的决定；
- 当前阅读器行为和用户数据 schema 已有兼容 fixture；
- 目标书籍包契约已经版本化；
- 《追寻敬虔》的迁移与回退路径已有文档；
- 已选定具有代表性的第二本书导入 fixture；
- 已定义导入、锚点、Context 和可迁移性的成功标准。

之后，只有通过明确架构决议，同时更新当前核心文档和验证契约，本草案才能转为有效规范。
