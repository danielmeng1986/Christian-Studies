# Christian Studies 产品规划书

**版本：** 0.2
**状态：** 已接受的规划基线——实施仍有门槛
**效力：** 规划文档，不是当前实现规范

> Agent 使用的英文主文档：[`Product-Plan.md`](Product-Plan.md)。

英文版是面向 Agent 的规划依据。产品决定必须经过中文审阅，并在同一次修改中同步到两个版本。两个版本发生冲突时，应暂停规划或实施，先完成核对。

## 1. 目的

本规划说明 Christian Studies 如何从一个已经可用的单本书阅读器，逐步发展为多书籍 AI 辅助阅读环境，同时不丢失当前系统已经证明有价值的特性。

它定义产品成果、实施顺序、重构门槛和成功标准；它不会预先选择所有实施技术，也不会让目标架构自动变成当前架构。已接受决定和剩余问题记录在 [`Open-Questions-zh.md`](Open-Questions-zh.md) 与 [`Decisions/`](Decisions/README-zh.md) 中。

## 2. 项目起点与产品洞察

项目最初的目标很简单：使用 Git 保存阅读基督教书籍时产生的想法和笔记。《追寻敬虔》暴露了一个实际问题：旧版 Word 书稿不便导航和注释，而经过审核的 Markdown 更适合阅读与维护。由 Markdown 构建 HTML 后，脚注、经文、选区笔记和更丰富的阅读交互成为可能。

之后开发的 AI 讨论功能揭示了更深层的产品价值。过去，读者需要上传整本书或手工把段落粘贴到普通聊天中；本地阅读器则可以针对当前问题组装准确的 Context：当前原文、临近结构、脚注、经文、个人笔记、人物身份匹配，以及本书其他章节的相关段落。

本项目的产品判断是：

> 对严肃阅读而言，AI 回答质量不仅取决于选择了哪个模型，更取决于是否围绕读者在书中的真实位置，组装出了透明、可追溯来源并适合当前任务的 Context。

Christian Studies 应当把 Context 变成用户可以检查和控制的产品能力，而不是隐藏在内部的实现细节。

## 3. 主要用户成果

这个环境应当帮助读者：

1. 导入自己合法持有的原始资料，同时不丢失原件；
2. 得到忠实、可审阅的 Markdown 阅读版本；
3. 在舒适的阅读环境中就近查看相关资料；
4. 把持久笔记附着在准确的原文位置；
5. 向 AI 提问时不再手工重建整本书的上下文；
6. 理解 AI 使用了什么证据，以及它不知道什么；
7. 控制个人资料和补充资料是否离开本机；
8. 从零散注释逐步形成经过审核的结构化知识；
9. 保留不依赖单一模型或 UI、可以理解和迁移的数据。

已经接受的第一版产品以本地优先和个人读者为中心。是否发展协作版或托管版，要先向项目所有者的读书会朋友验证需求，并通过新的产品决议。

## 4. 当前已经验证的基础

《追寻敬虔》的实际使用已经证明下列思路可行：

- 保留原稿来源链的 Word 到 Markdown 规范化流程；
- 以 Markdown 作为经过审核的阅读正文权威来源；
- 确定性生成 HTML；
- 交互式脚注、经文和选区注释；
- Git 可读的用户数据文件；
- 感知修订版本的本地 API；
- 按来源类型组织 Context；
- 每轮发送前可见、可选择的 Context；
- 跨章节检索与人物身份解析；
- 需要主动授权的补充资料库证据；
- 不依赖外部联网检索也能获得有用的 AI 回答。

这套基础是下一阶段需要提取和通用化的资产，而不是应该丢弃的临时原型。

## 5. 产品边界

### 平台方向包含

- 使用统一导入和阅读工作流管理多本书；
- 保存原件并维护经过审核的 Markdown 版本；
- 书籍目录和管理面板；
- 交互式阅读、参考资料、笔记与 AI 讨论；
- 与具体书籍无关的 Context 构建和检索；
- 兼顾成本与能力、且保留用户控制的模型选择；
- 受控的 MCP 工具和可复用技能；
- 经过人审的结构化笔记与跨书知识工作流；
- 可重现的生成、迁移、测试和评估。

### 已接受的分发模式

- **个人版：** 项目所有者机器上的持久内容、注释和讨论可以由 Git 管理。
- **内部版：** 读书会朋友在本地部署；共享书籍和资料可以使用 Git，每位读者的笔记与讨论只留在本地。
- **外部版：** 应用不附带书籍，可以附带允许再分发的圣经资源；读者自行导入受支持的材料。

开发阶段继续使用浏览器加 loopback 服务。第一个可分发版本以 Web 应用为基础打包成桌面应用。完整决定见 [ADR-0001](Decisions/ADR-0001-Product-Deployment-and-Distribution-zh.md)。

### 当前不预设

- 托管式多用户服务；
- 账户、协作或公开分享；
- 具体桌面套壳技术或操作系统支持矩阵；
- 自动接受 AI 的转换结果或神学结论；
- 以数据库作为当前注释和讨论的权威来源；
- 不受限制的网络、MCP、文件系统或模型访问；
- 在第一版平台中支持所有电子书和文档格式。

这些都是需要决定的问题，而不是隐含需求。

## 6. 交付策略

项目按可验证阶段推进，而不是先指定日期。每个阶段在实施前都必须有明确的进入和退出条件，并且不能破坏当前阅读器的可用性。

### 阶段 0——架构与决策基线

成果：在重构前明确记录当前职责和目标职责。

- 维护仓库工作契约和当前架构；
- 记录项目来历和平台方向；
- 决定影响存储、部署、内容表示和平台边界的关键问题；
- 盘点当前《追寻敬虔》的行为与测试覆盖；
- 建立未来实现必须保持兼容的测试样本。

这一阶段的决策门槛已经完成。当前行为盘点、兼容 fixture、首批版本化领域契约和迁移/回退提纲完成后，阶段 0 才正式结束。

### 阶段 1——提取稳定的领域契约

成果：在物理移动代码之前，先形成与具体书籍无关的契约。

- 定义 `Book`、`Edition`、`ReadingUnit`、`Reference`、`Annotation`、`Discussion`、`Source`、`ContextBundle` 和 `EvidenceManifest` 的身份；
- 把领域行为与《追寻敬虔》的路径及 UI 假设分离；
- 使用当前书籍作为兼容性 fixture 建立契约测试；
- 定义 schema 版本和迁移策略；
- 建立仓库级规范检查。

退出门槛：当前阅读器能够通过文档化的书籍无关接口保持原有行为，并且不移动权威用户数据。

### 阶段 2——建立书籍导入流水线

成果：新书可以从原始导入材料进入可审阅的阅读包。

- 保存导入原件，记录权利和来源元数据；
- 使用不同格式的适配器，不建立一个巨型转换器；
- 提供转换预览和诊断；
- 在 Markdown 成为权威正文前允许人工修正和批准；
- 验证结构、链接、引用和必要元数据；
- 使所有处理产物和索引均可重建。

退出门槛：至少再导入一本具有代表性的书，并且核心流水线中没有该书专用代码。

### 阶段 3——引入多书籍应用外壳

成果：前后端开始管理书籍，而不是固定指向一个目录。

- 增加书籍目录和生命周期状态；
- 通过稳定的应用接口提供书籍、章节、笔记、讨论、来源和构建操作；
- 在同一个管理面板中提供导入、验证状态、资料库管理和阅读入口；
- 让共享 Web 应用既能在开发阶段通过浏览器/本地服务使用，也能为之后的桌面套壳做好准备；
- 提供本地 Profile 初始化和本地 AI 提供商配置，不引入远程账户；
- 以垂直切片方式保留当前阅读能力；
- 所有写操作都只能通过经过验证且范围受限的 API 完成。

退出门槛：《追寻敬虔》和第二本书都能通过同一应用流程打开和研读。

### 阶段 4——通用化 Context 平台

成果：`ContextBuilder` 成为与具体书籍无关、可以评估的服务。

- 定义版本化的 Context 请求、Bundle、预览和 Manifest 契约；
- 分离证据发现、排序、用户选择、预算和 Prompt 渲染；
- 建立可重复的检索与回答质量评估用例；
- 保留逐来源授权和 Prompt Injection 边界；
- 把 Context 的可解释性作为正式 UI 能力。

退出门槛：同一条 Context 流水线可以处理多本书，同时不削弱来源标签、修订检查和用户控制。

### 阶段 5——加入模型编排

成果：模型选择能够平衡回答质量、延迟、隐私和成本。

- 使用透明的策略输入判断问题需要哪些能力；
- 在经过批准的模型或提供商之间选择；
- 在适当情况下允许用户明确覆盖自动选择；
- 记录模型、策略版本、预计成本和降级行为；
- 使用固定阅读问题评估路由效果；
- 当能力或提供商不可用时安全失败。

退出门槛：相对于单模型基线，路由表现出可测量的价值，同时没有让 Context 行为变得不透明。

### 阶段 6——加入 MCP 与技能能力

成果：外部能力可以扩展阅读流程，但不能绕过证据、授权或安全规则。

- 定义能力注册表和最小权限模型；
- 区分确定性处理工具和研究工具；
- 在预览和证据 Manifest 中显示工具使用；
- 防止导入内容作为指令控制工具；
- 测试拒绝、失败和来源追踪行为。

退出门槛：至少有一个范围严格受限的能力改善了真实阅读流程，并通过权限和来源追踪验收。

### 阶段 7——发展结构化知识

成果：注释和讨论可以形成经过审核、仍然链接到证据的知识。

- 从现有研读材料提出结构化笔记候选；
- 先评估一个已经读完的章节，判断其中的注释和讨论是否支持有用综合；
- 把 AI 建议与用户已接受知识分开；
- 保留指向章节、参考资料、讨论和外部证据的引用；
- 支持跨书的人物、概念、经文、事件和主题；
- 保持 Markdown 可读的导出或表示。

退出门槛：读者可以审核、接受、编辑、拒绝并追踪结构化知识建议，AI 不能静默修改持久知识。

## 7. 重构原则

平台应采用渐进式替换：

1. 先用测试和真实数据描述当前行为；
2. 在当前实现旁边定义新契约；
3. 先让一个完整垂直切片通过新契约；
4. 比较生成结果和用户数据行为；
5. 通过可回退或兼容方式有计划地迁移；
6. 只有新实现满足验收标准后才删除旧代码。

避免一次性重写。目录迁移、schema 迁移、前端替换、模型路由和新产品行为不应合并在同一次修改中。

## 8. 成功标准

| 领域 | 示例指标 |
| --- | --- |
| 导入忠实度 | 审核后的正文可回溯原件；未解决的转换问题明确可见 |
| 达到可读状态的时间 | 受支持来源可以用很少的书籍专用设置进入审核预览 |
| 阅读器耐久性 | 重建和正文修订不会让旧笔记静默锚定到错误文字 |
| Context 质量 | 固定评估集中必要证据存在，同时减少无关证据和无依据结论 |
| 可解释性 | 每轮 AI 回答都能显示来源类型、来源身份、修订、模型和工具使用 |
| 经济性 | 按任务类别测量成本和延迟；路由不能牺牲验收质量 |
| 可迁移性 | 书籍、审核正文、笔记和 Manifest 在脱离单一 UI 或提供商后仍可理解 |
| 可复用性 | 第二本书只需要配置和内容审核，不需要复制应用代码 |

每个阶段宣称成功之前，都应使用具体 fixture 定义其指标。

## 9. 主要风险

- 自动转换可能产生看似合理但不忠实的正文；
- 平台抽象可能抹去不同书籍特有的编辑需求；
- 正文修订可能使注释或讨论失去锚点；
- 检索可能只增加 Context 数量，却没有提高证据质量；
- 模型路由可能只优化价格，同时隐藏行为差异；
- MCP 工具或导入文档可能扩大信任和数据外发边界；
- 数据库可能成为不透明的第二真相来源；
- 结构化笔记自动化可能混淆用户判断和 AI 建议；
- 大规模重构可能中断当前可用的阅读环境。

每个阶段都必须把相关风险转化为测试、预览、权限或明确的用户决定。
