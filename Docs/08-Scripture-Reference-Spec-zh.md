# 8. 经文引用规范

**版本：** 1.0  
**适用范围：** 整个 Christian Studies 仓库  
**目的：** 让 Markdown 中的经文引用保持可读、可审计，并能在本地网页中从共享圣经语料库准确生成和展示经文。

本规范的英文版面向 AI 与自动化实现，见 [08-Scripture-Reference-Spec.md](08-Scripture-Reference-Spec.md)。中英文规则必须保持一致；若措辞有歧义，以英文版中的机器规则为实施依据，以中文版中的阅读体验为产品依据。

## 一、基本原则

1. Markdown 正文只记录经文引用，不复制保存整段经文。
2. `References/Bible-Texts/` 是经文文字、译本元数据与书卷映射的唯一权威数据源。
3. 构建程序在构建期解析并验证引用，只把当前章节实际需要的经文编译进网页。
4. 浏览器在运行期只负责显示、隐藏与切换已编译的译本，不加载整本圣经。
5. 原书中的引用显示文字必须保留，例如 `來11.39` 不得仅因默认译本是简体而改成 `来11:39`。
6. 新显示的经文必须标明译本；不得让读者误以为生成的经文就是原书采用的逐字引文。
7. 原书已经逐字引用的经文不得静默替换。语料库经文只能作为并列参考或补充显示。

## 二、权威文件与目录

```text
References/
├── Scripture.md
└── Bible-Texts/
    ├── manifest.json
    ├── books.json
    ├── citation-aliases.json
    └── versions/<translation>/verses.json

Books/<Book>/
├── Metadata/scripture-config.json
├── Reading/**/*.md
└── References/Scripture.md
```

- `manifest.json` 定义可用译本、显示名称、语言与许可。
- `books.json` 定义 66 卷的统一代码、简繁体全名与标准简称。
- `citation-aliases.json` 负责把原稿中的别名解析为统一书卷代码。
- `verses.json` 是实际经文内容。
- `Metadata/scripture-config.json` 定义一本书的默认译本与可选译本。
- 书级 `References/Scripture.md` 记录本书的特殊约定，不重复保存经文正文。

## 三、Markdown 经文链接

经文必须使用普通 Markdown 链接和 `scripture:` URI：

```markdown
[路4:23](scripture:LUK.4.23)
[路1:44-45](scripture:LUK.1.44-45)
```

链接显示文字以原稿为准；链接目标使用统一的大写书卷代码。

### 3.1 目标语法

```text
scripture:<BOOK>.<CHAPTER>.<VERSE-SPEC>[;<CHAPTER>.<VERSE-SPEC>][?version=<ID>]
```

其中：

- `<BOOK>`：`books.json` 中的统一代码，如 `GEN`、`LUK`、`HEB`。
- `<CHAPTER>`：十进制正整数。
- `<VERSE-SPEC>`：单节、连续范围或同章离散节号。
- `version`：可选，只决定首次打开时采用的译本；该译本必须在书级配置中。

合法示例：

```text
scripture:LUK.4.23
scripture:LUK.1.44-45
scripture:JER.36.3,8
scripture:1TH.1.5-10;2.13
scripture:1CO.2.4,5;15.25,26
scripture:LUK.1.44-45?version=kjv
```

第一版不允许一个链接横跨不同书卷；不同书卷必须分别建立链接。

### 3.2 标点与原文

- 显示文字可以保留原稿的 `:`、`：`、`.`、`．`、`-`、`–`、逗号和分号。
- URI 中只使用 ASCII `.`、`,`、`;`、`-`。
- 不为统一外观而修改 Word 原稿中的经文简称、数字或标点。
- 同章续引应包括在同一链接中，例如：

```markdown
[耶36:3, 8](scripture:JER.36.3,8)
[帖前1:5-10; 2:13](scripture:1TH.1.5-10;2.13)
```

## 四、书级译本配置

每本书使用：

```json
{
  "schema_version": 1,
  "default_translation": "cuv-s",
  "available_translations": ["cuv-s", "kjv"],
  "translation_labels": {
    "cuv-s": "新标点和合本简体",
    "kjv": "King James Version 1769"
  }
}
```

规则：

1. 默认译本必须出现在可选译本列表中。
2. 所有译本 ID 必须存在于共享 `manifest.json`。
3. Markdown 链接没有 `version` 时使用默认译本。
4. 链接指定 `version` 时以它作为首次显示译本，但卡片仍可切换到其他已配置译本。
5. 译本变化只需修改书级配置，不应批量改写正文链接。
6. `translation_labels` 可选，用于覆盖该书网页中的译本显示名；键必须属于可选译本，值必须是非空字符串。

《追寻敬虔》默认使用 `cuv-s`。

## 五、构建期处理

构建程序必须：

1. 识别所有 `scripture:` 链接，并把它们转换为不会跳转的交互链接。
2. 严格解析目标语法；拒绝未知书卷、无效章节、倒置范围或未配置译本。
3. 从每个已配置译本的 `verses.json` 读取相应经节。
4. 若某译本缺少被请求的独立经节记录，构建失败并报告译本与引用，不得静默退回其他译本。
5. 只将本章实际引用的经文编译为嵌入式 JSON 或等价静态资源。
6. 对相同的规范引用去重；正文中多个相同链接控制同一张经文卡片。
7. 保持构建确定性：相同 Markdown、配置和圣经语料必须产生逐字节相同的网页。

生成的正文链接至少包含：

```html
<a class="scripture-ref"
   href="#scripture-LUK.4.23"
   data-scripture-id="LUK.4.23"
   data-initial-version="cuv-s"
   aria-controls="reference-panel"
   aria-expanded="false">路4:23</a>
```

## 六、经文合并与署名

### 6.1 正文合并

- 去掉原始 VPL 每行开头的书卷代码、章号和节号。
- 中文译本的连续经节直接连接，不添加空格。
- 英文译本的连续经节用一个普通空格连接。
- 保留译本中的所有文字、标点、段落符号和方括号；不润色、不补标点。
- 离散节号与跨章续引按 URI 中的顺序连接。

### 6.2 引用行与译本标识

卡片顶部的译本选择器是当前译本的唯一标识。卡片底部只显示本地化书卷简称与经节范围，不重复附加译本名称。

中文译本使用简体或繁体标准简称：

```text
路 1:44–45
```

英文译本使用英文书卷名：

```text
Luke 1:44–45
```

内部代码如 `LUK` 不应作为默认的人机界面文字。译本选择器必须始终显示当前译本的完整显示名。

## 七、左栏交互

左栏是通用“脚注 / 经文”区域，不再是只容纳脚注的容器。

每个打开项目使用带类型的稳定键：

```text
footnote:12
scripture:LUK.4.23
```

行为规则：

1. 点击脚注或经文链接，在左栏打开相应卡片。
2. 再次点击同一链接，关闭相应卡片。
3. 脚注与经文可以同时打开。
4. “显示全部”打开本章所有脚注和经文；“清空”关闭所有项目。
5. 经文卡片提供译本下拉菜单，默认选中书级默认译本或链接指定译本。
6. 切换译本只改变当前卡片，不改变全书配置，也不修改 Markdown。
7. 打开的正文链接显示一致的激活状态，并维护正确的 `aria-expanded`。
8. 窄屏下沿用现有侧栏折叠行为。

## 八、笔记定位兼容性

脚注和经文链接的显示文字属于正文可见内容，但不属于笔记锚点的规范正文文本。笔记选择、偏移计算与重定位时必须排除 `.footnote-ref` 和 `.scripture-ref`，防止以后增加或修改链接破坏已有笔记位置。

## 九、检查门槛

一次实现只有在以下检查全部通过后才算完成：

1. Markdown 中每个经文引用有合法且唯一可解析的目标。
2. 每个目标在所有已配置译本中均能解析出请求的经节。
3. 中文经文无人工插入的节间空格；英文经文只有一个节间空格。
4. 经文卡片顶部显示当前译本名，底部显示不重复译本名的本地化引用行。
5. 点击、再次点击、关闭按钮、显示全部、清空和译本切换均正常。
6. 脚注原有行为无回归。
7. 笔记选择不能包含脚注或经文链接，已有笔记锚点保持稳定。
8. Safari 与 Chrome 的 localhost 使用方式均不依赖外部网络。
9. 重复构建结果一致，生成目录不包含整本圣经或机器本地路径。

## 十、版权与未来演进

- 只有允许完整存储、再分发及当前用途的译本可以加入共享语料库。
- 受版权保护的译本不得通过抓取网页的方式加入仓库；必须采用授权 API 或明确许可。
- 将来改用 REST API 时，应保持 `scripture:` Markdown URI、统一书卷代码和书级配置不变，只替换构建/读取层。
- 可以生成供人工审阅的章节经文清单，但它只能是派生物，不得成为与共享语料并列的第二份经文权威来源。
