# 《追寻敬虔》本地交互式电子书需求分析

> 中文审核版。对应的英文执行版：`interactive-ebook-requirements.md`。

英文版用于约束实施，中文版用于产品审核。产品决定一经确认，必须在同一次修改中同步到两个版本；如两者冲突，应先停止实施并完成对齐。

## 1. 文档目的

本文档用于确定《追寻敬虔》从校订后的 Markdown 生成本地交互式网页的产品范围、技术路线、数据结构和验收标准。

第一阶段以第五章《約翰．歐文論從神而來的交通》为原型。原型通过验收后，再把同一套构建流程应用于全书。

## 2. 已有输入

- 正文：`Reading/第2部分-清教徒与圣经/05-約翰．歐文論從神而來的交通.md`
- 脚注：`References/Footnotes-05.md`
- Word 原稿：`Original/QFG Draft 20170911 20211005.doc`
- Word 转 Markdown 规范：`Metadata/word-to-markdown-spec.md`

第五章正文已经具备可供程序识别的结构：

- YAML 元数据；
- 一个章标题和若干节标题；
- 普通段落、引用段落和斜体；
- 指向 `Footnotes-05.md` 中具体标题锚点的脚注链接。

因此，网页构建不应重新解释 Word 文件，也不应复制一份人工维护的正文。校订后的 Markdown 应当是网页正文的唯一内容来源。

## 3. 产品目标

本项目要形成一个离线优先、适合长时间阅读的本地电子书：

1. 忠实呈现 Markdown 中的正文结构和样式。
2. 阅读正文时，可在左栏查看、汇总或关闭脚注，而不离开当前位置。
3. 可选中正文文字，在右栏创建、编辑、保存和删除私人笔记。
4. 已有笔记的正文范围保持高亮，并可通过点击高亮重新打开笔记。
5. 阅读主题、笔记和界面状态在关闭页面后仍可恢复。
6. 后续能以同一规则生成全书网页，而不是为每章复制一套手写 HTML。

## 4. 非目标

第一阶段暂不实现：

- 经文检索与经文内容展示；
- 云端同步、多人协作和账户系统；
- 移动端完整的三栏编辑体验；
- EPUB、Kindle 或原生桌面应用打包；
- 富文本笔记、图片附件和手写批注；
- 跨章节全文搜索；
- 将网页笔记自动写回 Markdown 或 Word 原稿。

这些能力不应阻碍未来扩展，但不进入第五章原型的验收范围。

## 5. 推荐技术路线

### 5.1 结论

HTML、CSS 和 JavaScript 是当前需求最合适的基础技术。推荐实现为“本地静态网页应用”，由一个构建步骤把 Markdown 和脚注编译为网页资源，再通过本机 `localhost` 打开。

推荐结构如下：

```text
校订后的 Markdown + References
              ↓ 构建
      HTML + CSS + JavaScript
              ↓ 浏览器
      阅读界面 + 仓库内章节笔记 JSON
```

CSS 负责三栏布局、排版、主题和高亮；JavaScript 负责脚注交互、文字选择、笔记编辑和本地持久化；HTML 承载构建后的语义化正文。

### 5.2 为什么不建议只双击一个 HTML 文件

单一自包含 HTML 可以完成第五章演示，但不适合作为全书的长期工作流：

- 浏览器对 `file://` 页面读取其他本地文件有限制；
- 不同浏览器对本地文件的存储来源处理可能不同；
- 多章导航、共享样式和脚本会逐渐难以维护；
- 更新正文时，容易混淆生成文件和手工编辑文件。

因此建议提供一个简短的本地启动方式，在浏览器访问固定的 `localhost` 地址。网页本身仍完全保存在本机，日常使用不需要互联网。

### 5.3 技术路线比较

| 路线 | 优点 | 局限 | 结论 |
| --- | --- | --- | --- |
| 单一 HTML，直接双击 | 最简单、便于传递 | 多章维护、跨文件读取和持久化不稳定 | 只适合一次性演示 |
| 静态网页应用 + 本地服务 | 离线、轻量、易构建全书、浏览器兼容性好 | 打开前需要启动本地服务 | 推荐 |
| React/Vue 等前端框架 | 组件化和复杂状态管理方便 | 引入构建依赖，当前规模下收益有限 | 暂不需要；复杂度增长后再评估 |
| Electron/Tauri 桌面应用 | 可做真正的桌面应用和本地文件管理 | 打包、升级和维护成本明显增加 | 当前不采用 |
| EPUB | 适合普通电子书阅读 | 难以稳定实现本需求的三栏笔记交互 | 不适合作为主实现 |

第一版可以使用轻量构建脚本和原生 JavaScript，不依赖前端框架。第三方 Markdown 解析器若被采用，应在构建时使用并锁定版本，生成结果不得依赖联网加载。

## 6. 信息架构与页面布局

### 6.1 桌面端三栏

页面主体采用三栏布局：

| 区域 | 主要用途 | 建议行为 |
| --- | --- | --- |
| 左栏 | 当前打开的脚注；以后也可放经文 | 固定在视口内，内容独立滚动 |
| 中栏 | 章节正文 | 页面主要滚动区域，保证舒适行宽 |
| 右栏 | 笔记查看和编辑 | 固定在视口内，内容独立滚动 |

建议正文栏的实际文字宽度约为 42–48 个中文全角字符，左右栏各保留足够宽度显示脚注和笔记。三栏宽度可用 CSS 变量统一调整。

### 6.2 窄屏退化

第一阶段以桌面浏览器为主要使用环境。窗口不足以容纳三栏时：

- 中栏保持可读宽度；
- 左、右栏改为可开关的侧边抽屉；
- 不要求手机上同时显示三栏；
- 不能因为侧栏开关而丢失尚未保存的笔记。

### 6.3 顶部工具栏

建议提供一条简洁的固定工具栏，至少包含：

- 主题切换；
- 左栏显示/隐藏；
- 右栏显示/隐藏；
- 当前章节名称；
- 预留章节导航控件；第五章 MVP 中可显示为禁用或仅有一个选项的菜单；
- 笔记保存状态。

脚注的“全部显示”和“全部清空”放在左栏顶部；右栏顶部显示当前笔记状态。

## 7. 功能需求

### 7.1 Markdown 正文渲染

1. 构建时移除 YAML 元数据，但可把其中的书名、章号和来源信息写入页面元数据。
2. 按 Markdown 当前语义呈现标题、段落、引用、斜体和链接。
3. 不在浏览器中修改正文内容。
4. 正文中的脚注链接不执行普通页面跳转，而由脚注控制器接管。
5. 普通外部链接仍按普通链接处理，并应与脚注链接在视觉上有所区分。
6. 每个可批注的正文块应获得稳定标识，以支持笔记定位。

### 7.2 三种阅读主题

必须提供：

- 明色调：浅色背景、深色正文；
- 暗色调：深色背景、浅色正文；
- 护眼色调：低对比度暖色或浅茶色背景、深棕灰正文。

实现要求：

1. 颜色全部通过 CSS 自定义属性管理，避免三套重复样式。
2. 三栏、弹出按钮、输入框、链接、高亮和焦点状态必须随主题一起变化。
3. 主题选择保存在浏览器本地，下次打开时恢复。
4. 首次打开可跟随系统明暗设置；如果用户主动选择过主题，以用户选择为准。
5. 三种主题均需保证正文、链接、按钮和输入框有清楚的视觉对比。

### 7.3 脚注交互

1. 点击正文脚注链接，在左栏添加对应脚注卡片并将其置于可见位置。
2. 再次点击同一脚注链接，只关闭该脚注卡片。
3. 可以同时打开多个不同脚注，按用户点击顺序排列。
4. 左栏提供“显示全部”按钮，按脚注在正文中的次序显示本章全部脚注。
5. 左栏提供“清空”按钮，关闭当前所有脚注卡片。
6. 每张脚注卡片提供独立关闭按钮，并标明脚注编号。
7. 脚注卡片中的段落、斜体和链接应保留 Markdown 语义。
8. 脚注打开或关闭不得改变正文的滚动位置。
9. 当前已打开的脚注链接应有可辨识的激活样式。
10. 译者注等非纯数字锚点必须正常工作。

左栏内部的数据接口应预留内容类型，例如 `footnote` 和未来的 `scripture`，但第一阶段只实现脚注。

工具栏必须预留目录或章节下拉菜单的位置，即使 MVP 目前只有第五章。尚未构建的章节不得生成虚假链接。

### 7.4 创建笔记

推荐第一版只允许在一个正文块内选择连续文字；正文块包括段落、标题和单个引用段落。跨段选择列为后续功能，以避免复杂的高亮分割、重叠和正文修订恢复问题。

创建流程：

1. 用户在中栏选择非空文字。
2. 选择结束后，在选区附近显示“写笔记”快捷按钮。
3. 用户也可通过正文选区的自定义右键菜单触发“写笔记”。
4. 点击后，右栏打开新笔记编辑器，显示被引用的原文和空白笔记区。
5. 只有点击“保存”才创建笔记；取消则不留下高亮或空记录。
6. 纯空白选择、侧栏文字选择和跨越多个正文块的选择不创建笔记，并给出简短说明。

浏览器原生右键菜单不应被完全替换。自定义菜单应只在正文存在有效选区时出现，并保留一种能打开系统菜单的方式。选区后的浮动按钮应作为主要入口，右键作为辅助入口。

### 7.5 查看、编辑和保存笔记

1. 保存笔记后，编辑器默认关闭，正文选区显示高亮。
2. 点击高亮文字，在右栏打开对应笔记。
3. 右栏显示引用原文、笔记正文、创建时间和最后修改时间。
4. 已保存的笔记始终可编辑。
5. 编辑内容只有点击“保存修改”后才覆盖已存笔记。
6. 从有未保存修改的笔记切换到其他笔记或关闭侧栏时，应提示保存或放弃。
7. 删除笔记前要求确认；删除后同时移除正文高亮和本地记录。
8. 右栏在没有打开具体笔记时，显示本章笔记列表，可点击列表项定位正文并打开笔记。
9. 从笔记列表定位正文时，应将高亮滚动到视口内，但不应将文字贴在窗口最顶端。
10. 同一段正文可以有多个笔记；第一版不允许两个笔记的选区相互重叠。

### 7.6 笔记内容格式

第一版建议使用纯文本、多行编辑框：

- 保留换行；
- 不执行笔记中输入的 HTML；
- 暂不提供 Markdown 预览或富文本工具栏；
- 可在数据模型中保留 `format: "plain-text"` 字段，方便以后升级。

这样能先验证阅读与批注流程，避免富文本编辑器抢占项目复杂度。

## 8. 笔记定位与数据设计

### 8.1 为什么不能只保存字符序号

如果只保存“本章第 1340 到 1352 个字符”，Markdown 修订时在前面添加一个字，之后所有笔记都可能错位。只保存浏览器 DOM 路径也不可靠，因为 Markdown 渲染方式或行内斜体结构变化后，DOM 节点会变化。

因此，每条笔记应同时保存稳定块标识、块内位置和文字上下文。推荐的数据结构如下：

```json
{
  "schemaVersion": 1,
  "bookId": "qfg",
  "chapterId": "05",
  "notes": [
    {
      "id": "note-generated-id",
      "sourceRevision": "chapter-content-hash",
      "anchor": {
        "blockId": "chapter-05-p-17",
        "startOffset": 24,
        "endOffset": 39,
        "exact": "用户当时选中的原文",
        "prefix": "选区前的一小段文字",
        "suffix": "选区后的一小段文字"
      },
      "body": "用户写下的笔记",
      "format": "plain-text",
      "createdAt": "ISO-8601 time",
      "updatedAt": "ISO-8601 time"
    }
  ]
}
```

页面加载时按以下次序恢复锚点：

1. 先用 `blockId + startOffset + endOffset` 精确核对选中文字；
2. 如果正文已改变，则在原正文块内使用 `exact + prefix + suffix` 重新匹配；
3. 如果正文块标识也已变化，则在全章正文块中寻找带有相符前后文的唯一匹配；
4. 仍无法唯一匹配时，将笔记标为“需要重新定位”，保留笔记内容但不错误高亮。

构建器应根据正文结构生成稳定块标识。已有标识在正文小改时应尽量保持不变，不能每次构建都随机生成。

### 8.2 本地持久化

第一版以仓库内每章一个 JSON 文件作为笔记的唯一真实数据源。页面通过本机 `localhost` 服务读取和保存该文件，不使用 IndexedDB 持久化笔记。

直接解析一章的 JSON 笔记数据不会构成可感知的性能负担，而且可以避免浏览器数据库与仓库文件之间的双向同步和冲突。`localStorage` 只保存主题、栏位开关等少量界面偏好。

建议将笔记文件集中放在 `Notes/Annotations/`，例如第五章使用 `Notes/Annotations/05.json`。笔记文件属于项目源文件，应纳入 Git；生成网页不得内嵌或复制私人笔记。

由于 Safari 和 Chrome 中的普通网页都不能无提示地直接改写仓库文件，本地启动程序除提供静态资源外，还必须提供一个严格受限的笔记读写接口。该接口只能读写既定的章节笔记目录，不能接受任意文件路径。

保存要求如下：

- 每次创建、修改或删除笔记，都立即保存整章 JSON；
- 使用临时文件加原子替换，避免中途退出产生半个 JSON 文件；
- 写入前校验数据格式和章节编号；
- 文件使用 UTF-8、两空格缩进和稳定字段顺序，便于 Git 查看差异；
- 没有实际内容变化时不重写文件；
- 保存失败时保留编辑器内容并明确提示，不伪装为已经保存；
- JSON 文件仍可手工复制作为备份，但第一版不需要另做浏览器数据库导入、导出流程。

## 9. 构建与目录建议

建议将来源和生成结果严格分离：

```text
Books/追寻敬虔/
├── Reading/                 # 人工校订的 Markdown 正文
├── References/              # 脚注、经文和书目
├── Notes/Annotations/        # 每章一个、纳入 Git 的笔记 JSON
├── Metadata/                # 转换与网页规范
└── Web/
    ├── src/                 # 网页模板、CSS、JS 和构建逻辑
    └── dist/                # 自动生成、可在浏览器阅读的文件
```

工作流建议为：

1. 按 Word 原稿修订章节 Markdown。
2. 运行 Markdown 审计，确认正文、结构和脚注链接完整。
3. 运行网页构建命令。
4. 构建器读取 Markdown 与对应脚注文件，生成网页。
5. 运行本地服务并在浏览器中检查。
6. 笔记由本地服务直接保存到 `Notes/Annotations/`；不得混入生成的 HTML。

`Web/dist` 不纳入 Git。构建必须稳定、可重复，且生成结果不得包含笔记；网页源代码、构建配置和 `Notes/Annotations/*.json` 纳入 Git。

## 10. 状态与错误处理

需要明确处理以下情况：

- 脚注文件不存在或脚注锚点失效：正文链接显示警告状态，左栏给出可理解的错误，不跳到空白页面。
- Markdown 修订后笔记无法定位：保留笔记并列入“需要重新定位”，不可静默删除。
- 笔记保存失败：编辑内容继续留在输入框中，并显示错误。
- 章节 JSON 格式不正确：不写入文件，并保留最后一次成功读取的页面状态。
- 页面刷新时有未保存内容：浏览器离开前提醒。
- 多个浏览器标签页同时编辑同一笔记：至少检测更新时间冲突，避免后保存者无提示覆盖。

## 11. 隐私、安全与可访问性

1. 所有正文和笔记默认只在本机处理，不发送到网络。
2. 页面不得依赖 CDN 字体、脚本或样式；离线状态必须完整可用。
3. Markdown 和笔记内容不得作为未经处理的 HTML 执行。
4. 按钮和侧栏应能使用键盘操作，并有明显焦点样式。
5. 脚注链接应声明展开状态；侧栏和笔记状态应向辅助技术提供可理解的标签。
6. 不能仅靠颜色表达“有笔记”或“脚注已打开”；还应使用边线、图标或其他视觉提示。
7. 正文基础字号、行高和列宽应通过 CSS 变量集中设置，方便以后加入字号调节。

## 12. 第一阶段原型范围

第五章原型应包含：

- 第五章正文和全部 35 个脚注；
- 明、暗、护眼三种主题；
- 桌面三栏布局和窄屏侧栏退化；
- 单个或多个脚注的打开、关闭、全部显示和清空；
- 单个正文块内的文字选择与浮动“写笔记”按钮；
- 纯文本笔记的创建、保存、隐藏、重新打开、编辑和删除；
- 正文高亮和本章笔记列表；
- 每章一个 JSON 文件的读取和持久化；
- 本地服务提供受限、可靠的笔记读写接口；
- 正文小幅修订后的笔记锚点恢复与失配提示；
- 完全离线运行。

## 13. 第一阶段验收标准

### 阅读与主题

- 第五章的标题、八个分节、段落、引用和斜体均按 Markdown 正确呈现。
- 三种主题可以即时切换，刷新页面后保持上次选择。
- 三栏各自滚动时，不导致其他栏无故跳动。

### 脚注

- 正文每个脚注链接均能显示正确内容，包括两个译者注。
- 第二次点击同一链接会关闭对应脚注。
- 同时打开多个脚注后，“清空”可以一次关闭全部。
- “显示全部”能按正文顺序显示本章所有脚注。

### 笔记

- 选择一个正文块内的文字后，可以通过浮动按钮创建笔记。
- 保存后编辑器关闭，原文出现高亮；刷新后高亮仍存在。
- 点击高亮可打开正确笔记，并可修改后再次保存。
- 删除笔记后记录和高亮同时消失。
- 取消新建笔记不会留下高亮或空记录。
- 选区跨段或与已有笔记重叠时，系统阻止创建并说明原因。
- 关闭并重新启动本地服务后，可以从章节 JSON 恢复笔记及其高亮。
- 每次保存或删除后，对应章节 JSON 立即产生可供 Git 查看和提交的变化。

### 数据稳健性

- 在已批注段落之前新增普通段落并重新构建后，已有笔记仍能通过块内文本和上下文恢复。
- 无法可靠恢复的笔记会被列为“需要重新定位”，不会高亮错误文字或丢失内容。

## 14. 已确认的实施决定

1. 通过本机 `localhost` 访问。
2. 第一版正式支持 Safari 和 Chrome。
3. 第一版只允许在单个正文块内连续选择文字。
4. 第一版禁止笔记选区重叠。
5. 第一版笔记使用纯文本。
6. 每章笔记以仓库内对应的 JSON 文件为唯一真实数据源；第一版直接读取 JSON，不使用 IndexedDB。
7. `Web/dist` 不包含笔记；只要构建稳定、可重复，就不纳入 Git。
8. 正文笔记高亮统一使用橙色，并在三种主题下分别调整明度和对比度。

MVP 只实现章节笔记所需的最小本地接口。等多章节或更多资源确有需要时，本地 API 可以重组为更完整的 REST API；该演进不属于第五章 MVP 的范围。
