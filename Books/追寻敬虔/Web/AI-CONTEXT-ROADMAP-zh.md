# 《追寻敬虔》AI 上下文架构 Roadmap

状态：实施规划基线  
版本：1.0  
制定日期：2026-08-29  
适用范围：《追寻敬虔》本地阅读器“与 AI 讨论”功能  
产品规范：[`AI-CONTEXT-SPEC-zh.md`](AI-CONTEXT-SPEC-zh.md)  
AI 执行合同：[`AI-CONTEXT-SPEC.md`](AI-CONTEXT-SPEC.md)  
讨论持久化规范：[`AI-DISCUSSION-SPEC-zh.md`](AI-DISCUSSION-SPEC-zh.md)

## 1. Roadmap 的目标

本 Roadmap 将上下文规范转化为可实施、可测试、可逐阶段验收的工作。核心成果不是一段越来越长的 prompt，而是一个独立、确定、可审计的 `ContextBuilder`：它负责决定每轮 AI 实际看到哪些资料、这些资料来自哪里，以及为什么被选中。

Roadmap 不预设日历日期。每个阶段只有满足出口条件后才进入下一阶段。后续阶段不得以破坏当前阅读、笔记或本地讨论能力为代价提前实施。

## 2. 总体架构决定

### 2.1 职责边界

```text
Browser reading scene
        ↓
Discussion API / orchestration
        ↓
ContextBuilder
  ├─ acquire     读取允许的本地资料
  ├─ normalize   统一标识、文本和定位
  ├─ resolve     解析人物、译名、经文和锚点
  ├─ retrieve    检索笔记、本书章节和以后加入的资料
  ├─ rank        按来源与相关性排序
  ├─ budget      计算上下文规模，不静默截断
  └─ manifest    记录实际发送的证据
        ↓
ContextBundle { envelope, manifest, preview }
        ↓
Prompt adapter + OpenAI Responses API
        ↓
Persist discussion message + turn manifest
```

以下规则由代码强制执行，而不是只写进 prompt：

- 读取哪些文件；
- 哪些笔记与选区相交；
- 最多返回多少跨章节片段；
- 是否允许本地资料库或联网；
- 哪些可选证据被用户排除；
- 上下文是否超限；
- 本轮 manifest 与实际 API payload 是否一致。

运行时 developer instructions 只负责 AI 无法由代码代替的解释行为，例如区分作者原文、用户笔记、外部资料和模型背景知识。

### 2.2 建议模块边界

第一轮重构时采用项目当前规模所需的最小边界，避免过早拆成过多文件：

```text
Web/scripts/
  context_builder.py       # 编排、ContextBundle、预算和 manifest
  context_sources.py       # 章节、元数据、笔记、译名及以后资料源
  context_retrieval.py     # 跨章节与资料库确定性检索（进入相应阶段再建立）
  discussions.py           # 讨论 schema、持久化、prompt adapter
  serve.py                 # HTTP 路由、权限与流式响应
```

若实现初期 `context_sources.py` 内容很少，可以先保留在 `context_builder.py`，达到第二个资料源后再抽离。模块边界以可测试性为准，不以文件数量为目标。

### 2.3 核心数据对象

```python
ContextRequest
  book_id
  chapter_id
  anchor
  question
  discussion_id
  capabilities
  exclusions

ContextBundle
  envelope       # 交给 AI 的结构化证据
  manifest       # 可复现记录
  preview        # 给用户看的摘要与可选项目
  estimates      # 字符/token 估算和预算状态
```

`ContextBuilder` 不调用 OpenAI，不写讨论文件，也不修改书稿和笔记。它接收明确输入并返回普通数据结构，因此可以在不联网的单元测试中完整验证。

### 2.4 已确定的技术选择

- 第一阶段继续使用完整当前章节，不先做章节摘要。
- 本地检索先使用确定性文本检索；优先评估 SQLite FTS5，而不是立即引入向量数据库。
- `ContextBuilder` 的构建过程默认无网络副作用。
- 联网能力在独立阶段实施，默认关闭，并与一般网络扩展分开授权。
- OpenAI 托管 File Search 暂不采用；本地资料库先保持本地索引和片段级发送。
- manifest 按“每轮用户问题”保存，而不是只在讨论级记录一次。
- 新 schema 采用显式版本和迁移函数；不原地猜测旧数据含义。
- 当前 `store: false`、`truncation: disabled` 策略继续保持。

## 3. 里程碑总览

| 里程碑 | 对应规范层级 | 用户可见成果 |
| --- | --- | --- |
| M0：基线冻结 | 当前实现 | 已有讨论行为有测试保护，payload 可检查 |
| M1：ContextBuilder 骨架 | 第一层 | 书籍身份准确；请求组装不再散落在讨论模块 |
| M2：阅读现场 | 第二层 | AI 明确看到标题路径、选区所在段落及前后段落 |
| M3：个人研读与身份解析 | 第三层前半 | 相关笔记和译名命中可预览、排除并正确归属 |
| M4：本书跨章节检索 | 第三层核心 | AI 可引用本书其他章节的相关段落 |
| M5：预览、预算与可追溯闭环 | 横跨全部层级 | 用户知道本轮发送什么；每轮可由 manifest 复现 |
| M6：本地资料库 | 扩展第三层 | 可添加、审核、检索和排除其他本地材料 |
| M7：Bibliography | 第三层预留完善 | 脚注书目可解析并参与来源定位 |
| M8：可信来源联网查询 | 第四层 | 用户主动启用后进行受控、带引用的联网查询 |
| M9：深度研究与检索增强 | 第四层增强 | 可选多来源研究；是否采用语义检索由评估决定 |

M1–M5 构成本地上下文架构的第一个完整版本。M6 以后均为独立增量，不阻塞本地研读闭环。

## 4. 阶段 0：冻结当前行为与建立评估基线

### 工作

- 为当前 `build_response_input` 和 Responses API payload 建立快照或结构测试。
- 固定一组不包含私人内容的测试章节、选区、经文、脚注与多轮讨论 fixture。
- 记录当前 prompt、context schema、discussion schema 和 retrieval 版本。
- 建立“实际 payload 中没有 API Key、本地绝对路径和未声明资料”的安全测试。
- 建立现有阅读、笔记、讨论列表、新建讨论、继续讨论和 Markdown 回答显示的回归检查。
- 建立固定问题集的第一版人工评估表，至少覆盖：段落解释、脚注解释、经文联系、人物识别、资料不足时的诚实表达。

### 数据保护

- 所有写入测试只能使用临时目录和 fixture。
- 实施和测试不得修改用户正在使用的 `Notes/Annotations/05.json`。
- 不以真实讨论记录作为自动测试输入，除非先复制到临时目录并去除私人内容。

### 出口条件

- 当前 API payload 的字段、顺序和安全属性有自动测试保护。
- 重构前后的同一输入能够比较。
- 所有既有测试通过，且测试过程不改动真实笔记和讨论文件。

## 5. 阶段 1：ContextBuilder 骨架与第一层

### 工作

- 建立 `ContextRequest`、`ContextBundle` 和版本常量。
- 将 `discussions.py` 中的上下文组装移入 `ContextBuilder`，先保持行为等价。
- 从 `Metadata/book.yml` 读取书籍身份；不得从 prompt 常量或模型知识补全缺失值。
- 输出规范中的 versioned context envelope。
- 将英文规范第 16 节的精简规则改造成版本化运行时 developer instructions。
- 建立 prompt adapter：只负责把 `ContextBundle`、已完成历史和当前问题转换为 Responses API 输入。
- 让 `discussions.py` 继续负责消息状态和持久化，让 `serve.py` 继续负责 HTTP 与流式传输。

### 兼容策略

- 本阶段不改变用户界面。
- 现有讨论 JSON 继续可读。
- 若只重构内部结构，不立即升级持久化 schema。
- 重构后的 AI 输入至少包含重构前的完整章节、选区、经文、脚注和历史。

### 出口条件

- `ContextBuilder` 可在无 HTTP、无 OpenAI、无真实文件写入的条件下测试。
- 书籍身份来自 `book.yml`，缺失字段保持 `null` 或省略。
- 同一输入重复构建产生相同 envelope 和 manifest（时间字段除外，测试中应可注入时钟）。
- prompt adapter 不执行检索，也不自行读取仓库文件。
- 现有不联网讨论功能无回归。

## 6. 阶段 2：第二层——当前阅读现场

### 工作

- 建立章节 Markdown 的结构化 block map，包括稳定 `blockId`、标题路径、正文文本和源码定位。
- 将浏览器传来的锚点在服务器端重新验证，不直接信任客户端传来的段落内容。
- 解析：最近标题路径、选中 block、前一个正文 block、后一个正文 block。
- 保留完整当前章节，并额外发送邻近段落以提高显著性。
- 继续保留选区相交的全部经文和脚注快照及文档顺序。
- 对章节发生变化、锚点无法解析或选区内容不一致提供明确状态，不默默选择相似段落。

### UI

- 讨论选区卡显示所属小节。
- 上下文摘要从“完整章节、经文、脚注”扩展为“所属小节、邻近段落、经文、脚注”。
- 暂不要求展开完整 JSON；提供面向人的简洁摘要。

### 测试重点

- 章节开头和结尾没有前块或后块时正常工作。
- 引用块、列表、斜体和含链接文字的 block 定位正确。
- UTF-16 偏移与浏览器一致。
- 标题本身被选中、选区跨不支持的 block、正文修订变化均有明确行为。

### 出口条件

- AI 能明确引用选区所属小节和直接前后语境。
- envelope 中的 reading focus 可由章节源文件与锚点确定性重建。
- 当前完整章节没有因新增邻近段落而被删除或静默摘要。

## 7. 阶段 3：第三层 A——个人笔记与译名解析

### 7.1 个人笔记

#### 工作

- 只读加载当前章节笔记，复用现有锚点语义。
- 实现 `exact`、`overlap`、`sameBlock` 分类。
- 默认选择 `exact` 和 `overlap`；`sameBlock` 仅在规范允许时作为可选候选。
- 每条笔记标记 `evidenceType: user_note`、relation、ID、修订和更新时间。
- 笔记只用于构建上下文，不在构建过程中修改、迁移或重新保存。

#### UI

- 上下文预览列出将发送的相关笔记。
- 每条笔记可排除；排除只影响本轮，不删除原笔记。
- 明确显示“你的笔记”，避免与作者原文混淆。

### 7.2 译名与人物解析

#### 工作

- 加载 `References/追寻敬虔译名对照表.json`。
- 对选区、问题、标题路径及必要邻近段落进行 Unicode、空白、大小写和逗号式姓名规范化。
- 返回 `exact`、`alias` 或 `candidate`，保留原始字符串和 `sourceLine`。
- 为英文检索生成规范姓名，例如 `Owen, John` → `John Owen`，但不得改写来源摘录。
- 多候选和低置信度匹配不自动合并或作为检索事实。

#### UI

- 显示命中的中英文人名。
- 有歧义时允许用户选择或排除；未确认候选不进入后续自动检索。

### 出口条件

- 相同和重叠笔记分类正确，且 AI 将其称为用户的笔记。
- `約翰．歐文` 能确定性解析到 `Owen, John`。
- 译名命中不会被用作人物观点的证明。
- 本阶段读取但绝不修改 `05.json`。

## 8. 阶段 4：第三层 B——本书跨章节检索

### 工作

- 为全部 20 章及其脚注建立统一、可重建的检索文档。
- 每个检索单元保留 chapter ID、chapter title、heading path、block ID、正文、来源修订和脚注关系。
- 首先实现确定性候选生成：中英文人物名、别名、著作名、经文 ID、精确短语和问题关键词。
- 评估 SQLite FTS5/BM25；索引属于可删除重建的派生物，不成为正文权威来源。
- 排序遵循：同一人物精确命中 → 同一著作/经文 → 特征性神学短语 → 较宽主题。
- 默认最多 5 段、每章最多 2 段；不为凑数加入弱结果；排除当前选中 block 的重复内容。
- 返回完整段落或有边界的连贯摘录，并带 match reasons 与定位。

### UI

- 预览中新增“本书其他章节”。
- 用户可以展开片段、跳转到章节、排除单项或选择“查找更多本书内容”。
- AI 回答中的跨章节引用应可回到相应章节和 block。

### 评估

- 建立至少 20 个固定查询，覆盖人物、著作、经文、精确命题和无结果查询。
- 人工标记预期相关章节及明显误命中。
- 记录 Precision@5、无结果正确率、重复率和定位有效率。
- 不为提升召回而牺牲来源定位或加入大量弱相关文本。

### 出口条件

- 固定查询能稳定返回可定位且有解释理由的结果。
- 无相关内容时返回空数组，不报错、不编造。
- 用户排除的片段不进入实际 payload。
- AI 能区分当前章节与本书其他章节。

## 9. 阶段 5：预览、预算、冻结和 manifest 闭环

阶段 2–4 可以先使用逐步扩展的简化预览；本阶段完成规范要求的正式闭环。

### 工作

- 建立服务器端预览接口，输入 `ContextRequest`，输出 preview、候选证据、估算和一个短期构建标识。
- 用户发送时携带保留/排除选择；服务器重新验证并冻结最终 `ContextBundle`。
- 为 envelope 和最终 API payload 建立一致性检查。
- 使用实际模型 tokenizer（若依赖可稳定取得）或保守估算；必须清楚标注“估算”。
- 实现超限顺序：先减少可选网页、资料库、跨章节证据；不得静默删除当前章节、选区、经文、脚注或历史。
- 每轮用户消息保存一份 manifest；消息记录只引用该 manifest，不让后续检索变化改写历史。
- manifest 记录 schema、prompt、retrieval、source registry 版本，以及所有实际纳入证据的 ID、定位、修订和哈希。
- 为 schema 1 的旧讨论提供显式迁移或兼容读取；旧讨论没有 manifest 时标记 `legacyContext: true`，不得伪造历史 manifest。

### 建议持久化结构

优先在每个讨论文档中增加按轮记录，以保持讨论可整体移动和备份：

```json
{
  "schemaVersion": 2,
  "turns": [
    {
      "userMessageId": "...",
      "contextManifest": {},
      "contextSnapshot": {
        "optionalMutableEvidence": []
      }
    }
  ]
}
```

稳定本地资料可以只保存 ID、locator、revision/hash；网页和其他可变证据进入以后阶段时保存实际使用摘录或可复现快照。最终字段名在实施前用 fixture 验证，不因本示例强制采用 `turns`。

### 出口条件

- 发送前预览与最终 manifest 一致。
- manifest 与实际 API payload 一致。
- 用户能够明确排除所有可选资料。
- 超限时出现可理解的选择，不发生 Responses API 的隐式截断。
- 旧讨论可继续读取和继续讨论。

## 10. 阶段 6：本地资料库

### 工作

- 建立最终目录：

```text
Books/追寻敬虔/Sources/
  Originals/
  Processed/
  Indexes/
  catalog.json
```

- 原文件保持不变，导入生成带定位的 Markdown 或结构化文本。
- 第一批格式支持 Markdown、纯文本和 JSON；随后接入 PDF、DOCX 和受控 `.doc` 转换。
- 每份资料登记作者、题名、语言、类型、来源等级、神学传统、路径、许可说明、哈希和启用状态。
- 转换后必须显示预览并由用户确认，确认前不进入检索索引。
- 建立 `search_local_library` 的只读接口，默认最多返回 5 个连贯片段。
- 私人或敏感资料默认不启用；首次向 OpenAI 发送摘录前再次明确提示。
- 本地检索先复用 FTS/确定性基础设施，不上传完整资料库。

### UI

- “添加资料”与“联网查询”保持两个独立入口。
- 资料库页面支持启用/停用、查看元数据、转换预览、重建索引和移除派生索引。
- 删除原文件属于单独的明确操作，不随“从索引移除”一起执行。

### 出口条件

- 至少一种 Markdown、一种 PDF 或 Word 测试资料可以导入、定位、检索和排除。
- 原文件哈希与导入前一致。
- 索引删除后能从 Processed 内容完整重建。
- 只把用户确认的命中片段发送给 OpenAI。

## 11. 阶段 7：Bibliography 与脚注书目解析

### 工作

- 保持 `bibliographyMatches: []` 在此前所有阶段都是合法结果。
- 审计 20 章脚注中的书目格式、缩写、重复著作和页码表达。
- 为可确定的书目建立规范记录，同时保留脚注原文和来源位置。
- 不确定的作者、版本或出版信息进入待确认队列，不用模型猜测写入权威数据。
- 将书目记录连接到本地资料库条目和以后允许的外部原始文献定位。

### 出口条件

- 空 Bibliography 不影响讨论。
- 已解析记录能从脚注回到书目，也能从书目回到所有引用脚注。
- 歧义记录保持显式状态，不发生静默合并。

## 12. 阶段 8：第四层——可信来源联网查询

### 前置条件

- M1–M5 已完成并稳定使用。
- 本地检索和来源归属评估通过。
- 可信来源注册表已人工审核并版本化。
- 成本、超时、取消、缓存、引用保存和隐私提示已有明确 UI。

### 工作

- 建立机器可读 `trusted-sources.json`，落实规范中的来源等级、域名、语言、用途和限制。
- 实现独立能力状态：`local`、`web`；默认 `local`。
- 将“可信来源查询”和“扩大到一般网络”设为两个独立授权。
- 优先实现受控工具：`search_trusted_web` 与 `fetch_trusted_source`。
- 搜索词只使用必要的人物、著作和命题，不包含私人笔记、阅读历史、API Key 或本地路径。
- 网页内容去除脚本和导航，保留 URL、标题、作者、出版者、日期、访问时间、来源等级、有限摘录与哈希。
- 外部资料一律作为不可信证据；网页不能扩大权限、要求上传资料或触发其他工具。
- 对 OpenAI 内置 Web Search 与本地受控搜索做小规模比较；只有当域名控制、完整来源回传和审计满足规范时才可采用或混合使用。

### UI

- 输入区提供默认关闭的“联网查询”。
- 发送前显示将查询的主题、来源范围、预计额外成本/等待和取消入口。
- 可信来源无结果时询问是否扩大网络，不自动切换。
- 回答显示可点击来源及其 L1–L4/来源类型，区分原著与二手解释。

### 出口条件

- 关闭联网时没有任何外部查询。
- 可信模式不能访问注册表外域名。
- 所有外部主张保留可点击引用和本轮使用的证据记录。
- 页面中的 prompt injection 不能改变能力或数据边界。
- 超时、无结果、部分来源失败和用户取消均不会破坏本地讨论。

## 13. 阶段 9：深度研究与检索增强

### 深度研究

- 增加独立的 `deep` 能力，而不是把普通联网查询悄悄变慢。
- 显示研究计划、来源范围、进度、成本上限和取消能力。
- 对争议性主张进行多来源交叉核对，并明确异议与证据不足。
- 长报告仍必须回到可定位的本书、本地材料和外部来源。

### 语义检索决策门

只有当固定评估显示确定性检索持续漏掉重要同义表达时，才试验向量检索。试验必须：

- 与 FTS/BM25 在同一固定问题集上盲评；
- 保留原始 locator、来源等级和可解释 match reason；
- 作为候选召回增强，而不是绕过来源优先级；
- 记录索引模型、维度、切块和 `retrievalVersion`；
- 能完全删除并从本地资料重建。

若语义检索没有带来可感知的回答质量提升，则不进入正式架构。

### 出口条件

- 深度研究与普通讨论在 UI、成本和持久化中明确区分。
- 检索增强通过固定评估，不只依赖个别令人印象深刻的示例。
- 关闭 `deep` 后，M1–M8 的行为和性能不受影响。

## 14. 贯穿所有阶段的评估体系

### 14.1 三类测试

1. **确定性单元测试**：锚点、标题路径、笔记关系、译名、排序、预算、manifest。
2. **集成测试**：从浏览器请求到最终 Responses API payload；OpenAI 调用使用假客户端。
3. **回答质量评估**：使用固定问题集和人工 rubric，允许模型输出有措辞差异。

### 14.2 回答质量 rubric

每个问题至少评估：

- 是否直接回答用户问题；
- 是否准确理解选区与直接语境；
- 是否把本书其他章节正确归属；
- 是否把用户笔记标成用户观点；
- 是否利用人物译名而不把译名当证据；
- 是否避免不存在的引文、页码和联网声明；
- 是否在证据不足或来源冲突时表达不确定性；
- 是否真正带来联系、追问或洞见，而非只复述上下文。

“启发性”不可完全自动评分。每个里程碑保留少量真实阅读问题，由用户比较当前版本与上一稳定版本，并记录更有帮助、无变化或变差的原因。

### 14.3 安全与回归不变量

- 永不将 API Key 写入 payload、日志、讨论 JSON 或 manifest。
- 自动测试永不修改真实 `05.json`。
- 章节、附件和网页中的指令不获得开发者指令权限。
- 任何新资料源默认只读；写入或删除需要独立明确操作。
- 任何可选能力关闭后，基础本地讨论仍可运行。

## 15. 版本与迁移策略

独立维护：

- `discussionSchemaVersion`：讨论和消息持久化；
- `contextSchemaVersion`：envelope 与 manifest；
- `promptVersion`：运行时 developer instructions；
- `retrievalVersion`：规范化、检索、排序与预算；
- `sourceRegistryVersion`：本地和外部来源政策。

迁移规则：

1. 读取时先按原版本校验，再通过显式函数逐级迁移。
2. 自动迁移前备份或采用原子写入；失败时原文件保持完整。
3. 不为了添加 manifest 而伪造旧轮次的上下文。
4. schema 改动必须配套旧 fixture、迁移测试和回滚说明。
5. 在真实讨论文件上执行批量迁移前，先提供 dry run 和变更摘要。

## 16. 实施顺序与暂停点

推荐下一项实施工作是阶段 0，然后是阶段 1。M1 完成后暂停一次，用同一组真实阅读问题比较重构前后，确认行为等价，再进入阅读现场增强。

此后建议在以下节点进行真实使用验收：

- M2：标题路径和邻近段落是否让回答更贴近原文；
- M3：笔记与译名是否有帮助且没有喧宾夺主；
- M4：跨章节结果是否真正相关；
- M5：预览是否清楚但不过度打断讨论；
- M6：资料导入是否值得其复杂度；
- M8：联网结果是否比本地资料增加了可靠价值。

只有前一层稳定且用户能感知其价值，才继续扩大上下文来源。`ContextBuilder` 的目标不是发送最多资料，而是在清楚的来源边界内，持续选择最能帮助当前问题的资料。
